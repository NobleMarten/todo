# Аудит фронтенда после редизайна (2026-09-28)

Задача для агента-исполнителя: сделать так, чтобы PWA на iPhone («на экран Домой») ощущалась как
нативное приложение: плавно, без зума, с жестами. В этом документе — что проверено, что подтвердилось,
в чём причина и как чинить. Порядок разделов — порядок приоритета.

## Как проверялось

- Код: весь `frontend/src` (компоненты, хуки, `index.css`, `theme.css`), `index.html`, `nginx.conf`.
- Стенд: локальный API на отдельной БД, прод-сборка (`vite build`), прогон в Playwright:
  WebKit с профилем iPhone 15 и Chrome с настоящими touch-событиями через CDP
  (`Input.dispatchTouchEvent`). Считались сетевые запросы, размеры шита, шрифты полей ввода,
  работа свайпов до и после правки задачи.
- Второй заход — живой Chrome (расширение Claude in Chrome), прод-сборка на локальном API. В страницу
  ставились счётчики: `PerformanceObserver` (long tasks, layout shift), разрывы кадров через
  `requestAnimationFrame`, покадровый таймлайн состояния DOM после нажатия. Чтобы воспроизвести прод,
  `fetch` к API оборачивался задержкой **200 мс** — столько сейчас идёт запрос до VPS (замер `curl` до
  `http://95.85.252.88:8095/healthz`: 140–210 мс, один из пяти — **1,27 с**; с мобильного интернета больше).
- Что **не** проверялось, потому что нужен живой iPhone: реальный FPS прокрутки, поведение клавиатуры,
  пинч-зум в standalone-режиме. Такие пункты помечены «проверить на устройстве». Сортировку за ручку
  и перетаскивание на день в «Неделе» инструмент проверить не смог (он двигает мышь одним рывком).

### Главный вывод второго захода
На локальном API в Chrome **ни одной long task и ни одного пропущенного кадра** ни при открытии
карточки, ни при переключении вкладок, ни при отметке задачи. JS и React сами по себе не тяжёлые.
Ощущение «тормозит» создаёт то, что **почти каждое действие ждёт сеть** (см. 3.1, 3.3), а изменения
на экране происходят **скачком, без анимации** (см. 3.10). На iPhone к этому добавляются более
медленный процессор (там 3.4 и 3.5 уже заметны) и задержка мобильной сети.

Контекст деплоя, который влияет на выводы: прод открывается по `http://95.85.252.88:8095`, то есть
**без HTTPS и без домена**. Service Worker работает только на HTTPS (или localhost), так что офлайн-кэш
и мгновенный холодный старт сейчас недоступны в принципе.

## 1. Зум на iPhone (жалоба пользователя) — ПОДТВЕРЖДЕНО

### 1.1 Автозум при фокусе на полях < 16px — ✅ этап 1
iOS увеличивает страницу, если у поля, получившего фокус, `font-size < 16px`, и после этого масштаб
не сбрасывается. Все текстовые поля уже 16px, но вот что осталось (найдено в WebKit, `getComputedStyle`):

| Где | Элемент | Размер |
|---|---|---|
| Карточка задачи → «дедлайн» | `input[type=date].date-native` (`DatePicker.tsx`) | 14px |
| Карточка задачи → «делаю» | `input[type=date].date-native` | 14px |
| Карточка задачи → «повтор» | `select.date-native` (`RepeatField.tsx`) | **11px** |
| Строка задачи без дат → иконка календаря | `input[type=date].date-native` (`TaskRow.tsx`, `.date-assign`) | 14px |

Причина: `button, input, textarea { font: inherit }` в `index.css`, а у `body` `font-size: 14px`;
`select` в этом правиле вообще не указан. Поля прозрачные (`opacity: 0`), поэтому размер шрифта никто не заметил.

**Исправление:** `.date-native { font-size: 16px; }` (поле невидимо, на вёрстку не влияет) и добавить
`select` в reset-правило. Заодно правило-страховка: `input, textarea, select { font-size: max(16px, 1em); }`
или явная проверка в ревью.

### 1.2 Пинч-зум и зум двойным тапом не запрещены — ✅ этап 1
- `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` — нет
  `maximum-scale=1, user-scalable=no`.
- `touch-action` на `html` — `auto` (проверено), т.е. двойной тап по пустому месту/тексту зумит.
- Нет обработчика `gesturestart` (Safari игнорирует `user-scalable=no` для пинча, но уважает
  `preventDefault` у gesture-событий).

**Исправление (всё вместе, по отдельности на iOS не хватает):**
1. viewport: `width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover`.
2. CSS: `html { touch-action: manipulation; }` — убирает зум двойным тапом, пан и пинч остаются браузеру
   (у `.swipe-body` свой `pan-y`, у `.grip` — `none`, их не трогать).
3. В `main.tsx`: `document.addEventListener('gesturestart', e => e.preventDefault())`
   (+ `gesturechange`), чтобы гасить пинч. Проверить на устройстве в standalone-режиме.

### 1.3 Связь зума со свайпами
Если страница осталась увеличенной после фокуса на поле даты/повтора, горизонтальное движение пальца
двигает увеличенный viewport, а не строку — свайп «не работает». Это возможная причина жалобы №2,
если имелся в виду свайп строки (см. 2.3). После пункта 1.1 это уходит.

## 2. «Нет свайпа после правки задачи» (жалоба пользователя) — ПОДТВЕРЖДЕНО (в части шита)

### 2.1 Карточку задачи нельзя закрыть жестом — ✅ этап 2
`Sheet.tsx` — это `motion.div` без `drag`: у него есть «грабер» (`.sheet-grabber`), который выглядит как
ручка, но тянуть его нельзя. Закрыть можно только крестиком или тапом по фону.

### 2.2 Тапнуть по фону на телефоне почти негде — ✅ этап 2
Замер на iPhone 15 (393×659): шит `height: 647px`, начинается с `y: 12`. `max-height` =
`100dvh − safe-area-top − 12px`, а контента в карточке (дедлайн, делаю, повтор, подзадачи, заметка,
кнопки) больше экрана — шит всегда почти на весь экран. Видимого фона остаётся 12px, и в PWA они под
статус-баром. Тап по `(20, 20)` шит не закрыл. **Единственный способ закрыть карточку — крестик
в левом верхнем углу**, до которого на телефоне далеко тянуться.

В живом Chrome: протягивание шита от грабера вниз на 500 px шит не закрыло, зато **выделило весь текст
карточки** (заголовок, подписи полей, кнопки). На iPhone тот же жест даёт выделение и лупу, а не закрытие.
Значит, в шите, кроме полей ввода, нужно `user-select: none` (см. 3.9).

**Исправление:** drag-to-dismiss как у нативного bottom sheet:
- `drag="y"`, `dragConstraints={{ top: 0 }}`, `dragElastic={{ top: 0, bottom: 0.6 }}`, `dragMomentum={false}`;
- старт жеста — через `useDragControls` от шапки (`.sheet-grabber` + `.sheet-top`) всегда, а от тела шита —
  только если `sheet.scrollTop === 0` и палец идёт вниз (иначе конфликт с прокруткой содержимого);
- в `onDragEnd`: `offset.y > 120 || velocity.y > 600` → анимировать `y` до высоты шита и затем `onClose()`;
  иначе пружиной назад в 0;
- затемнение фона привязать к `y` через `useTransform`, чтобы фон светлел вместе с жестом;
- не начинать drag, если палец лёг в `textarea`/`input` с фокусом.
- Заодно добавить **анимацию закрытия**: сейчас шит монтируется условием `taskId !== null && <TaskSheet/>`
  в `App.tsx` без `AnimatePresence`, поэтому при закрытии он исчезает рывком. Обернуть в `AnimatePresence`
  и дать `exit={{ y: '100%' }}`.

### 2.3 Свайп строки после правки — в эмуляции и в Chrome работает
В Chrome с настоящими touch-событиями: свайп влево открыл «удалить» (`translateX(-96px)`) и до
открытия карточки, и после правки (приоритет + заголовок, закрытие крестиком). В живом Chrome то же:
правка приоритета, заголовка и заметки → закрытие крестиком → свайп влево открывает «удалить»;
свайп вправо в списке переносит задачу в «сегодня». Правки сохраняются (проверено через API).
Логика `SwipeRow` здесь в порядке. Если на реальном iPhone свайп строки после правки всё-таки пропадает — первая гипотеза
пункт 1.3 (остался зум после фокуса на поле даты). Проверить на устройстве после исправления зума.

### 2.4 Нет жеста «назад»
В standalone-PWA на iOS нет системного свайпа от края «назад» (он есть только в Safari с адресной
строкой). Экран списка (`/lists/:id`) и карточку можно покинуть только кнопкой. Желательно: свайп
от левого края (первые ~20px) → `navigate(-1)` на экранах без таб-бара и на шите. Не обязательно
в первом заходе, но сильно добавляет «нативности».

## 3. Плавность (жалоба пользователя) — ПОДТВЕРЖДЕНО, причины ниже по весу

Главное: «тормоза» — это в основном не медленный JS, а **ожидание сети на каждом шаге + скелетоны +
перерисовки во время анимаций**. Нативное ощущение даёт мгновенный ответ интерфейса, а данные
подтягиваются в фоне.

### 3.1 Каждое переключение вкладки — заново загрузка со скелетоном — ✅ этап 3
Экраны размонтируются при переходе (`<Routes>` в `App.tsx`), а данные живут в `useState` хуков
(`useDay`, `useTasks`, `useProjects`, `useSmartCounts`, `useWeek`…). Кэша между экранами нет.
Проверено: при переходе на «неделю», «списки», «итоги» и **обратно на «сегодня»** каждый раз
показывается `.skeleton`, и уходят запросы заново. На VPS без HTTP/2 и с RTT до сервера это
видимая пауза на каждой вкладке.

Покадровый таймлайн в Chrome с задержкой 200 мс (как до VPS):

| Переход | Что на экране |
|---|---|
| → «неделя» | 7 мс: скелетон, 0 строк → 245 мс: 8 строк |
| → «сегодня» (уже были на ней) | 24 мс: скелетон → 234 мс: 7 строк |
| → «списки» | 20 мс: скелетон → 230 мс: 12 элементов → 264 мс: ещё один (второй запрос) |
| → «сегодня» ещё раз | 12 мс: скелетон → 228 мс: строки |

То есть **каждое** переключение вкладки — это четверть секунды скелетона, а при сетевом всплеске
(1,27 с в замере) больше секунды. Вместе с `.screen { animation: fade-in }` это и выглядит как «мигание».

**Исправление (самое важное в документе):** stale-while-revalidate-кэш данных на уровне модуля.
Варианты:
- взять TanStack Query (`staleTime` ~30 с, `gcTime` минуты, `placeholderData`), переведя хуки на него —
  сразу закрывает 3.1, 3.2, 3.3;
- либо маленький свой кэш: `Map<key, {data, at}>` в `lib/`, хук сначала отдаёт кэш (без скелетона),
  потом тихо перечитывает; `notifyChanged` инвалидирует ключи.
Скелетон показывать только если кэша нет вообще (первый запуск).
Дополнительно: кэш можно класть в `localStorage`/IndexedDB, тогда и холодный старт PWA будет
мгновенным (показать вчерашнее → обновить).

### 3.2 Одна мутация → лавина перечитываний — ✅ этап 3
`lib/sync.ts` рассылает «данные изменились» всем подписанным хукам, каждый перечитывает всё своё.
Замеры:
- отметить задачу выполненной на «Сегодня»: `PATCH /tasks/2` + `GET /day` ×2 + `GET /projects` ×2
  (`useDay.run` сначала делает `await refresh()`, потом `notifyChanged(refresh)`, и `useProjects` на экране
  и в других местах перечитывается);
- правка в карточке (приоритет, заголовок, заметка — 3 правки): 3× `PATCH` + 3× `GET /tasks/:id` +
  3× `GET /day` + **6× `GET /projects`**;
- экран «Списки»: `useSmartCounts` делает 5 параллельных `GET /tasks?limit=1` на каждое открытие
  **и на каждый `notifyChanged`**; «Итоги» — ещё несколько `GET /tasks` + `/stats/activity`.
Каждый ответ — `setState` → перерисовка всего экрана, иногда прямо во время анимации.

**Исправление:** с кэшем из 3.1 — точечная инвалидация (менять задачу в кэше из ответа PATCH, а не
перечитывать всё); `useProjects` не должен перечитываться от изменения задачи (проекты меняются редко;
счётчики задач в проектах — отдельный лёгкий запрос или считать на клиенте); перечитывания
дебаунсить (~300 мс) и схлопывать одинаковые запросы в полёте. На бэкенде желательно одно
`GET /tasks/counts` вместо пяти запросов со `limit=1` (новый эндпоинт под существующим префиксом `/tasks`).

### 3.3 Карточка задачи открывается «пустой», потом прыгает по высоте — ✅ этап 3
`TaskSheet` при открытии делает `GET /tasks/:id` и `GET /projects`, хотя строка списка уже знает
задачу. Пока ответа нет, в шите крутится спиннер, потом шит резко вырастает до ~650px — прыжок идёт
одновременно с пружинной анимацией въезда.
Замер в Chrome при задержке 200 мс: 11 мс — шит высотой **151 px** со спиннером; 238 мс — спиннер
пропал, шит скачком **676 px**. Закрытие: через 17 мс шита уже нет (анимации ухода нет, см. 2.2).
**Исправление:** передать задачу из списка как начальные данные (через кэш из 3.1 или
`location.state`), рисовать карточку сразу, подзадачи догружать в фоне; `useProjects` брать из кэша.

### 3.4 Открытие карточки перерисовывает все строки списка — ✅ этап 5
`useOpenTask()` вызывает `useLocation()`, а он есть в **каждой** `TaskRow` (и `FocusCard`,
`SubtaskPanel`). Любая навигация (открыть/закрыть шит = смена URL) перерисовывает все строки ровно
в момент анимации шита. Нигде нет `React.memo`, `TaskRun` создаёт новые колбэки на каждый рендер.
**Исправление:** `useOpenTask` без подписки на location — читать текущий location в момент клика
(например, `useNavigate` + ref, обновляемый в одном месте, или `router.state`); `TaskRow` обернуть
в `memo` и сделать колбэки стабильными (передавать `task.id` + стабильные функции). Либо включить
React Compiler (`babel-plugin-react-compiler` в `vite.config.js`) — линт-правила под него уже стоят,
код к нему готов; он сам мемоизирует.

### 3.5 Полноэкранный «шум» поверх всего приложения — ✅ этап 6
`.grain` в `index.css`: `position: fixed; inset: 0; z-index: 100` + SVG `feTurbulence` с
`numOctaves='4'` как фон. Это отдельный слой на весь экран поверх всего контента при прозрачности
2,5%. На iOS полноэкранные фиксированные слои с SVG-фильтром — известный источник дёрганой прокрутки
и лишней работы композитора; визуально он почти незаметен.
**Исправление:** убрать совсем или заменить на маленький заранее отрисованный PNG (`background-repeat`),
и не держать поверх контента (`z-index: -1` на фоне `body`). Проверить на устройстве, но удаление
дешёвое и ничего не ломает.

### 3.6 Шрифты грузятся с Google Fonts — ✅ этап 7
`theme.css` начинается с `@import url('https://fonts.googleapis.com/...')` — цепочка: CSS → CSS шрифтов →
woff2 с другого домена. `display=swap` → при каждом холодном старте текст сначала системным шрифтом,
потом перескакивает на Geist (сдвиг вёрстки). Из России Google Fonts может отвечать медленно.
**Исправление:** самохостинг (`@fontsource/geist`, `@fontsource/jetbrains-mono` или woff2 в `public/`),
только нужные начертания и подмножества (latin + cyrillic), `<link rel="preload" as="font" crossorigin>`
для основного начертания. Либо системный шрифт (`-apple-system`) — это то, что делает интерфейс
«как родной» на iPhone.

### 3.7 Hover вместо active: нет отклика на нажатие — ✅ этап 6
В CSS много `:hover` (`.chip:hover`, `.box-btn:hover .box`, `.check-hit:hover .check`, `.picker-row:hover`…)
и почти нет `:active`. На iPhone `:hover` «прилипает» после тапа и остаётся до следующего тапа
в другом месте, а мгновенной реакции на касание нет — из-за этого нажатия ощущаются «ватными».
**Исправление:** все hover-стили завернуть в `@media (hover: hover) { … }`, добавить `:active`-состояния
(лёгкое затемнение/`transform: scale(.97)` с `transition` 80–100 мс) для кнопок, строк, чипов, табов.

### 3.8 Резинка и прокрутка фона — ✅ этап 6
- Нет `overscroll-behavior: none` на `html, body` — в standalone-PWA вся страница тянется резинкой,
  таб-бар и шапка «плавают».
- `Sheet.tsx` блокирует прокрутку фона через `body.style.overflow = 'hidden'` — на iOS Safari это не
  останавливает прокрутку/резинку фона при протягивании. Проверить на устройстве; надёжный вариант —
  `position: fixed` на `body` с сохранением `scrollY`, или `overscroll-behavior: contain` на шите
  (уже есть) плюс `touch-action: none` на `.sheet-backdrop`.

### 3.9 Мелочи, которые тоже вносят вклад — ✅ этап 6 (кроме бандла — этап 8)
- (✅ этап 2 — в шите) Нет выделения/callout только у `.swipe-body`; у остального UI долгое нажатие выделяет текст и
  открывает меню. Для «нативности»: `user-select: none; -webkit-touch-callout: none` на `body`,
  а `text`/`auto` вернуть полям ввода и заметке.
- Тема применяется в `useEffect` (`useTheme.ts`) — после первой отрисовки. У пользователя со светлой
  темой при старте мелькает тёмная. Исправление: маленький inline-скрипт в `index.html`, который до
  загрузки бандла ставит `data-theme` и `theme-color` из `localStorage`.
- Бандл одним куском 457 КБ (144 КБ gzip); framer-motion подключён целиком через `motion.*`.
  Можно `LazyMotion` + `m.*` (−~25 КБ gzip) и ленивую загрузку редких экранов
  (`ArchiveScreen` с `Activity`, `WeekScreen`, `SearchScreen`) через `React.lazy`. Эффект меньше, чем
  у пунктов 3.1–3.4, делать после них.
- `.screen { animation: fade-in }` на каждый экран — вместе со скелетоном даёт «мигание» при каждом
  переключении вкладки. С кэшем из 3.1 fade-in для вкладок лучше убрать (нативные табы переключаются мгновенно).
- `Sheet`: `useEffect(..., [onClose])`, а `closeSheet` в `App.tsx` пересоздаётся на каждый рендер —
  обработчик Escape и `body.style.overflow` переустанавливаются на каждый рендер App. Не баг,
  но стабилизировать через `useCallback`.

### 3.10 Изменения списков происходят скачком (найдено в Chrome) — ✅ этап 4
Мутации оптимистичные и быстрые: отметка «выполнено» на «Сегодня» — через 21 мс строка уже убрана,

## 4. Почему Avito (и хорошие PWA) ощущаются как нативные

Коротко — за счёт того, что интерфейс **никогда не ждёт сети и не блокирует палец**:

1. **Кэш-первые данные.** Экран рисуется сразу из памяти/IndexedDB, данные обновляются в фоне
   (stale-while-revalidate). Скелетон — только при самом первом запуске. → у нас пункт 3.1–3.3.
2. **Service Worker + HTTPS.** Оболочка приложения (HTML/JS/CSS/шрифты) отдаётся из кэша SW
   мгновенно и офлайн; холодный старт с экрана «Домой» — доли секунды. → у нас невозможно без HTTPS
   (см. раздел 5).
3. **Анимации только `transform`/`opacity`** на композиторе, без перерисовок React во время анимации,
   без полноэкранных фильтров. → пункты 3.4, 3.5.
4. **Нативные жесты:** тянущиеся шиты, свайп «назад», мгновенная подсветка нажатия (`:active`),
   нет «прилипшего» hover. → пункты 2.1, 2.4, 3.7.
5. **Отключены браузерные артефакты:** зум (viewport + `touch-action: manipulation` + 16px в полях),
   резинка (`overscroll-behavior`), выделение текста и callout, серая подсветка тапа. → пункты 1, 3.8, 3.9.
6. **Системный или самохостный шрифт** без скачка вёрстки. → пункт 3.6.
7. **Оптимистичные мутации без лавины перезапросов** — ответ сервера патчит кэш точечно. → пункт 3.2.

## 5. Инфраструктура (зона владельца, не код фронта)

- **HTTPS обязателен** для Service Worker (офлайн-оболочка, быстрый холодный старт) и даёт HTTP/2
  (параллельные запросы по одному соединению — пять `GET` счётчиков перестанут выстраиваться в очередь).
  Нужен домен (можно бесплатный вроде duckdns) + Let's Encrypt на host nginx.
- После HTTPS: `vite-plugin-pwa` (Workbox) — precache бандла, `StaleWhileRevalidate` для шрифтов,
  `NetworkFirst` с коротким таймаутом для GET API (или кэш данных в IndexedDB из пункта 3.1).
- Внимание: auth-кука и `VITE_API_URL` — см. CLAUDE.md, при переезде на домен оставить относительные
  запросы (пустой `VITE_API_URL`).

## 7. Как проверить результат

- В WebKit/iPhone-эмуляции: `getComputedStyle` всех `input, select, textarea` в карточке ≥ 16px;
  `getComputedStyle(document.documentElement).touchAction === 'manipulation'`.
- Переключение вкладок туда-обратно: второй заход на вкладку — без `.skeleton` и без блокирующего запроса.
  Проверять с искусственной задержкой API (обёртка `fetch` на 200–500 мс), на localhost проблема не видна.
- Карточка открывается сразу полной высоты, без спиннера (покадровый замер высоты `.sheet`).
- Прокрутка вкладки и списка восстанавливается после «назад» и после переключения табов.
- `.quick-add-row` по ширине равен строкам списка.
- Отметка задачи: не больше одного `PATCH` + одного фонового `GET` на экран.
- Шит: протягивание вниз на 150px закрывает; на 50px — возвращается; прокрутка содержимого шита
  не закрывает его.
- На живом iPhone в режиме «на экран Домой»: фокус на «дедлайн»/«повтор» не зумит; пинч и двойной тап
  не зумят; прокрутка длинного списка без рывков; нажатия подсвечиваются сразу.

### Этап 2 — закрытие карточки жестом (2.1, 2.2, `user-select` в шите)
Сделано:
- `lib/sheetGesture.ts` (+ тесты): пороги и решения жеста — `decide` (чей жест: шита или прокрутки;
  «мёртвая зона» 6 px), `blocksScroll` (гасить ли `touchmove` до решения), `shouldDismiss`
  (сдвиг > 120 px или скорость > 600 px/с), `velocity` (по точкам последних 100 мс).
- `Sheet.tsx`: шит тянется вниз 1:1 (вверх — нет), фон светлеет вместе с жестом (`useTransform`),
  отпустили до порога — пружина назад, после — шит доезжает вниз и закрывается. От шапки (грабер +
  строка с крестиком) тянется всегда, от тела — только если содержимое прокручено до верха и палец
  идёт вниз. Жест не начинается в поле ввода с фокусом. Клик сразу после жеста гасится.
- Анимация ухода: `AnimatePresence` вокруг `TaskSheet` в `App.tsx` и вокруг меню списка в
  `ProjectScreen.tsx`, `exit={{ y: '100%' }}` 220 мс; фон гаснет вместе с шитом. Уходящий шит
  пропускает касания (`pointer-events: none`) и не вызывает `onClose` второй раз (`useIsPresent`).
- `.sheet { user-select: none; -webkit-touch-callout: none }`, полям ввода и заметке — `text`.

Решения:
- Жест написан на pointer-событиях + нативный `touchmove` с `passive: false`, а не `drag="y"` framer-motion.
  Причина — iOS: если первый `touchmove` не погашен, Safari начинает прокрутку (резинку) шита и шлёт
  `pointercancel`, после чего framer жест уже не получит. `touchmove` гасится только когда шит у верха
  и палец идёт вниз (или жест от шапки), так что прокрутка содержимого не затронута.
- Отдельный слой `.sheet-backdrop-fill`: снаружи — появление/уход фона (`initial/exit`), внутри —
  прозрачность от жеста; на одном элементе эти анимации спорили бы за `opacity`.
- Escape и закрытие по фону теперь идут через «latest ref», поэтому эффект с `keydown` и
  `body.style.overflow` больше не переустанавливается на каждый рендер `App` (это половина последнего
  пункта 3.9; `useCallback` для `closeSheet` — на этапе 6).
- Меню списка (тот же `Sheet`) получило жест и анимацию ухода заодно: это один компонент.

Замеры (Chrome, профиль iPhone 15, touch через CDP, задержка API 300 мс):

| Сценарий | до | после |
|---|---|---|
| протянуть за шапку на 150 px | шит на месте | закрыт |
| протянуть за шапку на 50 px | шит на месте | вернулся (`top` 12 px) |
| тело у верха, 150 px вниз | — | закрыт |
| прокрутить содержимое вверх, затем тянуть тело вниз | — | прокрутка (29 → 0 px), шит на месте |

`touchmove`) и не показывает лупу/меню; поведение жеста при открытой клавиатуре.

### Этап 3 — кэш данных без ожидания сервера (3.1, 3.2, 3.3)

**Выбор: свой маленький кэш, а не TanStack Query.** Сравнение:

| | TanStack Query | свой кэш |

### Этап 5 — лишние перерисовки (3.4)
Сделано:
- `lib/opener.ts`: `openTask(id, task)` читает `navigate` и `location`, которые `App` кладёт туда в
  `useLayoutEffect`; `useOpenTask()` просто возвращает эту функцию. Строки, `FocusCard`, `SubtaskPanel`,
  `DoneRow` больше не подписаны на адрес. Важная деталь: в `BrowserRouter` подписан на адрес и
  `useNavigate`, так что «`useNavigate` + ref» из аудита не помог бы — нужен именно вынос из строки.
- React Compiler (`babel-plugin-react-compiler` в `vite.config.js`): мемоизирует элементы экранов в `App`
  (открытие шита не перерисовывает экран) и обработчики в экранах.
- `TaskRow` — `memo`, колбэки получают задачу (`onToggle(task)`, `onSetDue(task, d)`, `onDelete(task)`,
  `onToday(task)`): экран передаёт одну функцию всем строкам, `TaskRun` передаёт их как есть.
- `lib/cache.ts`: `shareEqual` (structural sharing, + тесты) — ответ сервера переиспользует неизменённые
  объекты (элементы массивов сопоставляются по `id`), при полностью равном ответе подписчики не
  оповещаются. Без этого фоновый `GET /day` после каждой правки давал новые объекты всем задачам,
  и `memo` строк не срабатывал.

Решения:
- Компилятор, а не ручные `useCallback`: без него `memo(TaskRow)` не работает — обработчики экранов
  создаются заново на каждый рендер (замерено: 18 перерисовок строк на одну правку вместо 2), а экран
  под шитом перерисовывается от `App` (9 строк на открытие). Ручной вариант — `useCallback` во всех
  экранах и `useMemo` для `<Routes>` — больше кода и хрупкий к будущим правкам. Цена: бандл
  146,3 → 163,9 КБ gzip (+17 КБ, +12 %) — это выход компилятора (кэши мемоизации), сама обработка babel
  размер не меняет (замерено). Частично отыгрывается на этапе 8 (`LazyMotion`, ленивые экраны).
- Компилятор молча пропускает `useSuggestions` и `useArchive` (`try … finally`), `useSearch`,
  `reorder` в `useTasks` (`i++` в замыкании) и `useScrollRestoration` (подавленное правило линта). Их
  колбэки и так на ручных `useCallback`, переписывать ради компилятора не стал — вне пункта.
- Замер: счётчик вызовов `TaskRow` во временной сборке (не в коде). Счётчик в теле экрана пришлось
  убрать: запись в `window` во время рендера — побочный эффект, и компилятор пропускал экран, портя замер.

Замеры (WebKit, iPhone 15, «Сегодня» с 9 строками, задержка API 300 мс; число вызовов `TaskRow`):

| закрыть карточку | 9 | 9 | 9 | 0 |
| отметить задачу в плане | 16 | 16 | 16 | 0 |

Регрессия: этапы 1–4 (свайпы, жест шита, кэш и число запросов, анимация схлопывания, прокрутка,
быстрый ввод с докруткой, удаление с «вернуть»), обход экранов — без изменений, ошибок в консоли нет.
